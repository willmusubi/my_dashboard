# 实作计画

在产品与 UI 关卡皆已批准后使用此流程。

## 步骤

1. 阅读已批准的功能规格书与情境包。
2. 确定可能会变更的文件。
3. 定义 API、数据与状态（state）契约。
4. 指定风险等级。
5. 以 `ai/templates/task-card.md` 为模板，将工作拆分为小型任务卡，产出到 `ai/artifacts/<Epic>/task-cards/<卡片id>.md`（见 `ai/artifacts/README.md`）。
6. 确保每张任务卡都符合 `ai/process/definition-of-ready.md`。
7. 若风险为中或高，在实作前停下来等待批准。

## 全端功能拆分规则

若一个 User Story 同时涉及前端与后端，默认拆成三张任务卡，而不是一张大卡：

1. 前端（画面、互动、状态管理）。
2. 后端（API、数据模型、商业逻辑）。
3. 前后端串接（实际串接 API、处理载入／错误状态、端到端验证）。

这样每张卡维持「一次只做一件事」，风险与验证范围也更容易掌握。纯前端或纯后端的工作不需要硬套这个三分法。

## Epic 架构优先规则

拆某个 Epic 底下的任务卡之前，先判断：这个 Epic 底下的多个 User Story，是不是共用同一组画面框架、路由保护，或数据模型？

- 若是，且这组共用基础目前还没有任何已完成（`stage: done`）的任务卡建立过，要先拆一张「{Epic 名称} 架构基础」任务卡，内容是把这组共用基础（例如后台的 layout、权限中介层、核心数据表）一次做好；同一个 Epic 底下接下来建立的其他任务卡，都要在 `dependsOn` 数组里列上这张架构基础卡的 id。
- 若某个 Epic 范围单一、User Story 之间不共用架构或数据模型，不需要套用这条规则，避免小 Epic 被过度拆卡。

**与「项目设置」Epic 的连动**：功能卡确实要用到 Epic 0 的某个产出时（例如要用
登录框架、要用 design token），才把那张卡的 id 写进 `dependsOn`。

> 上游此处要求「必须列上『项目设置』Epic 底下**全部**卡片的 id，不是『有用到才列』」，
> 与 `project-kickoff` 步骤 2 的强制规则互为镜像。两处都已在本 fork 删除——
> 那是一道完全序列化的屏障，会让任何功能 Epic 在 Epic 0 全部完成前寸步难行。

## 任务拆分的 MECE 检查

拆完任务卡后，回头核对，不可直接视为完成：

- **完全穷尽（CE）**：所有任务卡合起来，要能覆盖这个 User Story 的完整验收标准；若规格书里有提到、却没有任何任务卡负责，代表有缺口，要补一张卡或修正既有任务卡的范围。
- **相互排斥（ME）**：任务卡之间不能有重叠的职责（例如两张卡都要改同一支 API 或同一个组件的核心逻辑）；每张卡的边界要写清楚，避免实作时界线不清、互踩。

## 输出

- 架构笔记。
- 任务卡。
- 依赖关系（`ai/templates/task-card.md` 的「前置任务（dependsOn）」字段，对应看板卡片的 `dependsOn`）。
- 验证计画。
- 所需的审查关卡。

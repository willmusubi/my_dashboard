# 项目启动（Project Kickoff）

适用于全新项目，或既有项目要一次性建立完整的 Epic → User Story → Task 待办清单时。目的是把「这个项目要做什么」逐层拆解成看板上的任务卡；每一层都要停下来让人工勾选确认，不能自己闷头把三层全部生完才回报。

## 步骤

### 1. 项目规格澄清

在提出任何功能模块之前，先确认：

- 部署目标（例如：Vercel、自架 server、App Store、内部工具）。
- 技术栈（语言、框架、数据库、认证方式）。
- 已知的硬性限制（预算、排期、既有系统整合）。

用最少的问题把这些问完；用户已经讲清楚的部分不要重问。

### 2. 项目设置（Epic 0）：建议先做，但不阻塞其他 Epic

多数新项目应该先有一个 Epic「项目设置」，写进 `tools/kanban/epics.json`。
**用 AskUserQuestion 确认要不要建、以及包含哪几个 User Story**——已经有骨架的项目、
或只是往既有代码库加功能，往往不需要整个 Epic 0。

> 上游原文写的是「不得用 AskUserQuestion 问用户要不要做」+「全部完成才能往下走」。
> 那条规则叠加服务端的依赖阻断（`server.mjs` 的 `checkDependsOn`），实际效果是：
> 在建完一个 10+ 组件的组件库之前，写不了任何一行功能代码。本 fork 已解除。

依步骤 1 已确认的技术栈／部署目标，决定这个 Epic 底下要包含哪些 User Story（不适用的类别就不建立，例如纯后端项目不需要 UI 设计系统这个 User Story）：

- 技术骨架初始化（项目初始化、目录结构、基础 dependency、build/lint/test 管线、部署设定）。
- 环境变量与金钥设定（`.env.example`、密钥存放规范）。
- 核心数据模型／认证框架基础（跨 Epic 共用的核心数据表或登录机制，若项目有的话）。
- UI 设计系统／风格指引（若项目有 UI）。见下方「步骤 2a」，产出写进 `ai/context/design-system.md`，
  作为后续所有 Epic 做 UI 时的单一事实来源。

这些 User Story 选定后，跟其他 Epic 一样，用 `implementation-plan` skill 依需求拆成有明确规格、范围、验收标准的任务卡（不是一个类别一张大卡）；若某个 User Story 范围还不清楚，一样可以先用 `spec-interrogation` skill 澄清。

这个 Epic 底下的任务卡：

- `epic` 一律填「项目设置」，`userStory` 对应到上面选定的 User Story 名称。
- `order` 给比其他 Epic 的卡片都小的值，让看板上永远排最前面。
- `dependsOn` 一律是空数组（它们是依赖图的根，其他任务卡会依赖它们，它们不依赖任何人）。

**依赖只按真实需要列**：某张功能卡确实要用到 Epic 0 的某个产出（例如要用登录框架、
要用 design token），才把那张卡的 id 写进 `dependsOn`。

> 上游原文是「必须列上『项目设置』Epic 底下**全部**卡片的 id，不是『有用到才列』」。
> 那是一道完全序列化的屏障：任何功能 Epic 的第一张卡都被钉死在 Epic 0 全部完成之后，
> 哪怕它跟 Epic 0 毫无关系。本 fork 已删除该规则。
> `dependsOn` 的服务端阻断保持不变——依赖图不被下毒之后，它是个有用的安全网。

### 2a. UI 设计系统：推荐的展开顺序（项目有 UI 才做）

若项目有 UI，设计系统建议按由下而上的顺序推进：框架 → 风格 → design token →
组件库 → 版面。核心原则是**不要一步到位直接画版面**——没有 token 和组件库
就画出来的版面，后面每张 UI 卡都会各画各的。

**这是推荐顺序，不是五道强制关卡。** 规模由项目大小决定：小项目可以把 S1–S3
合成一张卡（定框架 + 定风格 + 出 token 文件），S4 只做当下真正用得到的组件，
用到新组件时再补并登记回 inventory。真正值得保留的人工关卡只有一个：
**S2 的风格方向（2-3 个 style tile 让人选一个）**——这是整套流程里最值钱的
一步，出 2-3 个变体停下来等人选，比任何事后 review 都有效。

> 上游把 S1–S5 写成五道各自独立的人工批准关卡，并要求 `dependsOn` 串成
> S1→S2→S3→S4→S5 的硬链。对个人项目来说，那意味着写第一行功能代码之前
> 先过 5 道关、从零建 10+ 组件的组件库。本 fork 已改为推荐而非强制。

所有阶段的定案都写进持久化的 `ai/context/design-system.md`（见该模板）。这份文件是后续所有功能 Epic 做 UI 时的单一事实来源。

**S2–S5 全程套用 `ai/skills/design-craft.md` 的设计工艺纪律**（type scale、4 的倍数间距、色彩系统分阶、depth 三选一、实作前先比对高质量开源参考），确保产出的不只是「有走完流程」，而是达到与高质量 production 产品同级的视觉水准。

- **S1 — 底层框架与组件库策略**。依步骤 1 的技术栈，决定 UI 框架、组件库是「采用现成（如 shadcn/ui、MUI、Ant Design）」还是「自建」、以及样式方案（如 Tailwind、CSS-in-JS、CSS Modules）。作法同步骤 6 的「探索现成包」：列 2-3 个合理选项、附优劣与自己的建议。**人工关卡：选定框架与组件库策略**，写进 `design-system.md` 的「底层框架」。
- **S2 — 视觉风格方向**。针对选定框架，产出 2-3 个 **style tile**（风格方向，不是完整版面）：每个变体呈现色彩情绪、字体个性、圆角与阴影倾向、密度、亮／暗模式与 1-2 个参考产品，让人工比较「整体气质」。这是 `ui-mockup-gate` 的风格方向变体。**人工关卡：选定一个风格方向**，写进 `design-system.md` 的「风格方向」。
- **S3 — Design Token**。从选定的风格方向，定义 primitive token（完整色票、字级 scale、字重、行高、间距 scale、圆角、阴影、z-index、动效时间与曲线）与 semantic token（如 `color.primary`、`color.surface`、`color.danger`、`space.page` 等语意层）。全部列进 `design-system.md` 的「Design Token 列表」；若项目已有可跑的框架，顺带在项目内产出真实 token 档（如 `tokens.css`／Tailwind 主题／theme 档）并在文件里记录其路径。**人工关卡：批准 token**。
- **S4 — 核心组件库**。**只用 S3 的 token** 做出基础组件（至少涵盖 button、input、select、checkbox/radio、card、nav、modal/dialog、table、form、toast/alert，依项目需要增减），每个组件涵盖必要状态（默认、hover、focus、停用、载入、错误）。做一个就登记进 `design-system.md` 的「组件库 inventory」（组件名／状态／用到的 token／文件位置／截图）。**人工关卡：批准组件库**。
- **S5 — 各界面版面 mockup**。到这一阶段才依步骤 1 判断的主要界面／用户端（例如管理员后台、顾客前台，各自一张任务卡）套用 `ui-mockup-gate`，用**已定案的 token 与组件库**拼出 2-3 个完整版面（layout）变体——整体版型、信息架构、导览与内容区配置。**人工关卡：每一端各选定一个版型**，记录于 `design-system.md`。

这些阶段用 `implementation-plan` skill 拆成范围明确的任务卡（`userStory` 都对应
「UI 设计系统」）。**卡片粒度和是否合并由项目规模决定**，不必一阶段一张。
`dependsOn` 只在后一阶段确实要用到前一阶段的产出时才列（S3 的 token 确实要
S2 的风格定案，这条值得列；其余按实际情况）。若某阶段范围还不清楚，可先用
`spec-interrogation` 澄清。纯后端项目不建立这个 User Story。

### 3. 提出功能模块（Epic）并让用户勾选

依照项目主题，主动发想一组合理的功能模块候选清单，不要空手叫用户自己想。**先把完整候选清单写下来、数一下总数，再套用下方「候选清单呈现规则」决定要问几轮**，用多选问题（例如 AskUserQuestion）列出候选项目，让用户勾选要哪些、或补充遗漏的模块。

用户勾选确认后，不能就地照候选清单的原始顺序写入，要先帮这些 Epic 排出构建顺序：判断每个 Epic 对其他 Epic 的影响范围——越是核心数据模型、主要用户旅程、其他模块都会依附的底层需求，排越前面；越是周边、独立、可有可无的小功能，排越后面。这个顺序**不用再让用户勾选**，用一段文字简短说明排序理由即可（例如「先建 A 因为 B、C 都会用到它的数据模型」），不用等待批准；用户若觉得顺序不对，才依指示调整。

选定的每个 Epic，依上面排好的顺序写进 `tools/kanban/epics.json` 的 `epics[]`（`name` / `definition`）；数组顺序就是看板「蓝图」分页的显示顺序，也是步骤 6 决定先做哪个 Epic 的依据，Epic 0「项目设置」永远排在最前面，不受这个排序规则影响。

### 4. 针对每个 Epic 提出用户需求（User Story）并让用户勾选

对每一个已选定的 Epic，主动发想这个模块底下合理的用户需求候选清单。**同样先数过总数、套用下方「候选清单呈现规则」**，一样用多选方式让用户勾选确认或增删。

选定的每个 User Story，写进对应 Epic 底下的 `stories[].name` / `definition`。

若某个 Epic 的范围还不清楚，先用 `spec-interrogation` skill 产出这个 Epic 的功能规格书（`ai/artifacts/<Epic>/feature-spec.md`）；规格书里的「User Stories」章节就对应这里勾选出的列表。

### MECE 检查（适用于步骤 3 与步骤 4，在呈现候选清单给用户之前完成）

脑力激荡候选清单时，不能只凭直觉条列、也不能只从用户已经明讲的需求出发，要用 MECE（相互排斥、完全穷尽）当质量门槛，并以「市面上同类系统常见的标准功能模块／需求」为外部基准。

- **完全穷尽（CE）**：先判断这个系统属于哪一种常见类型（例如电商、SaaS 后台、预约系统、内容平台、社群、内部工具），在心里列一份这类系统的「业界标准模块地图」，再逐一核对目前的候选清单是否涵盖。特别留意容易被漏掉的骨架型模块：认证与权限、通知、搜寻／筛选、审计纪录、后台管理、报表／仪表板、设定／偏好。缺的要主动补上再交给用户勾选，不能因为用户没提到就跳过。
- **相互排斥（ME）**：候选之间不能有职责重叠或边界模糊的情况。若两个候选其实是同一件事的不同说法（例如「会员系统」与「登录系统」高度重叠），要先合并或讲清楚各自边界，才能拿去问用户；不要把会混淆用户判断的重叠候选都丢出去问。
- User Story 层级同样适用：同一个 Epic 底下的 User Story，要覆盖这个模块的完整用户旅程（例如建立／查看／编辑／删除／搜寻、正常路径与例外路径），而不是只列一两个最直觉的情境；彼此之间也不能是同一个情境的重复描述。

### 候选清单呈现规则（适用于步骤 3 与步骤 4，强制检查，不可省略）

多选问题工具（例如 AskUserQuestion）**一题最多 4 个选项、一次调用最多 4 题**——等于一次调用最多摊开 16 个候选项，这是工具的硬性上限，无法在单次调用里绕过。**不得因为这个界面限制，就把脑力激荡出的候选清单砍到只剩 4 个或 16 个**，这会让用户误以为看到的就是全部、实际上却漏看了本来可能更好的候选。

**调用 AskUserQuestion 之前，强制自问并回答这一题：「我刚刚脑力激荡出的候选总数是多少？」** 把这个数字明确写出来，再决定轮数，不要没算过总数就先丢一题 4 选项出去。

- 候选数 ≤ 4：一题问完。
- 4 < 候选数 ≤ 16：拆成多题（依主题分组，例如「核心模块／延伸模块」），在**同一次调用**里一起问完（一次调用最多 4 题）。
- 候选数 > 16：**必须拆成多轮、多次调用 AskUserQuestion**，不能只调用一轮就当作问完了。每一轮调用前都要在文字消息中明确告诉用户「这是第 N 轮，总共约 M 个候选，还有更多」；跑完所有轮次、汇总完用户在每一轮的勾选结果之后，才能进入下一步骤。
- 用户永远可以用「其他」字段手动补充，但这只是补充机制，不能取代主动穷举候选、主动分轮呈现的责任。
- 若某一题刚好 4 个选项全被选走，代表这个分类可能还有没摊开的候选，必要时主动追加一轮确认是否有遗漏。
- **完成检查**：在汇总 Epic／User Story 列表前，回头确认「已呈现给用户的候选总数」是否等于「脑力激荡出的候选总数」。若少于，代表漏问了几轮，必须补问，不得直接视为完成。

### 5. 拆分任务（Task）并推上看板

对每个已选定的 User Story，用 `implementation-plan` skill 拆成任务卡，全端功能依该 skill 的「全端功能拆分规则」默认拆成前端／后端／前后端串接三张卡；若该 Epic 需要先立架构基础，依该 skill 的「Epic 架构优先」规则先拆架构基础卡。

每张任务卡都要建立成 `tools/kanban/` 底下一张真实卡片（一卡一个 JSON 档，`stage` 从 `backlog` 开始），并设定 `epic` / `userStory` 对应到上面选定的名称，让看板的「蓝图」分页能正确归类、算出完成度。除了步骤 2 规定的「每个功能 Epic 第一张卡要 dependsOn 全部『项目设置』卡片」，同 Epic 内若套用了架构基础卡，其余卡也要在 `dependsOn` 填上该架构基础卡的 id。`backlog` 车道内的 `order` 也要照步骤 3 排好的 Epic 顺序给值，较前面（较底层／较基础）Epic 的任务卡 `order` 要比较后面 Epic 的任务卡小，让看板从上到下就是建议的构建顺序。

### 6. 逐一任务的实作循环

每次只处理一张已在看板上、状态为 `ready` 的任务卡。若同时有多张卡都是 `ready`，优先选 `epics.json` 中排序较前面（较底层／较基础）Epic 底下的那张，同一个 Epic 内再依 `order` 由小到大处理，不要跳着挑周边小功能先做：

1. **若是前端任务，开工前一律先读 `ai/context/design-system.md`**，把 Epic 0 定案的风格方向、design token 与组件库 inventory 载入情境。这个任务要用到的 token 与组件，**能用既有的就必须用**，不得自己另立新色、新间距或重造已有的组件。
   - 若对应画面还不存在，跑 `ui-mockup-gate`，做 2-3 个 mockup 让用户选一个——mockup **必须用 `design-system.md` 的 token 与组件拼出来**，不得凭空发明新风格；选完才进入下一步。既有功能的小调整可跳过 mockup，但一样要遵守 token／组件重用规则。
   - 若这个任务需要的组件在 inventory 里还没有：**强制走「查库→照风格补做→登记回库」**——依既有 token 与风格新做该组件（涵盖必要状态），完成后登记回 `design-system.md` 的组件库 inventory，再继续本任务。不得为了赶进度就地捏一个一次性、不入库的组件。
2. 探索是否有现成包或框架可以解决这个任务，避免自己重复造轮子。若有 2-3 个合理选项，列出来问用户要用哪个并给出自己的建议；只有一个明显选择时才不用问。
3. 开始实作。每个阶段性成果都要让系统维持「完整可用」的状态，不能留下写一半、会让系统坏掉或启动不了的半成品。
4. 自己检查正确性：写并跑过单元测试与整合测试，不是只凭肉眼看代码。
5. 确认没问题后，把看板上这张卡的状态往前推（`implementing` → `verify` → `done`），并视情况记录验证证据（用 `test-verification` skill，以 `ai/templates/verification-report.md` 为模板产出到 `ai/artifacts/<Epic>/verification/`）。

### 7. 资安纪律（每一张任务卡都要做，不是只有高风险才做）

实作当下就要套用 `ai/checklists/security-checklist.md`，包含但不限于：

- 不得以明文存储密码或密钥。
- 检查 OWASP Top 10 相关风险。
- 高风险项目（认证、金流、个资、基础设施）仍需额外走 `ai/process/review-gates.md` 的 Security Gate。

## 输出

- 已确认的技术栈与部署目标。
- `tools/kanban/epics.json` 内已选定的 Epic 与 User Story，含固定排最前面的「项目设置」Epic，其余 Epic 依基础程度由大到小排序。
- 若项目有 UI：已填写的 `ai/context/design-system.md`（框架、风格方向、design token、组件库 inventory、各界面版面），由 Epic 0 的五阶段流程逐步产出。
- `tools/kanban/cards/` 内对应的任务卡（含 `epic` / `userStory` / `dependsOn`）。
- 逐张任务卡的实作与验证纪录。

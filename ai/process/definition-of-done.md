# 完成定义（Definition of Done）

任务只有在「实作」与「验证证据」两者都存在时，才算完成。

## 必要证据

- 变更的文件。
- 行为变更摘要。
- 执行过的命令。
- 测试输出摘要。
- Lint／类型检查／build 输出（如适用）。
- UI 变更的截图或视觉比对。
- UI 变更的设计系统对照：列出重用的 token 与组件；若新做了组件，
  确认已依既有 token／风格制作并登记回 `ai/context/design-system.md` 的组件库 inventory。
- 高风险变更的安全性备注。
- 已知限制。
- 后续任务。

证据写进卡片的 `evidence` 字段（`commands` / `findings` / `residual`），
不要只写在聊天里——聊天会被关掉，卡片不会。

## 残留风险（residual）怎么写

`evidence.residual` 的每一条，都必须让读的人能立刻回答一个问题：
**现在要不要有人跟？**

- **要有人跟** → 写明归宿：卡号，或明确的时机。
  例：「留言写入 API 还没做，**在 DASH-009**」
- **不用跟** → 写明理由，以及（如果有）将来重新评估的触发条件。
  例：「跨文件非原子……对拖拽重排来说是排序错乱而非数据丢失，已记录不另建机制」
  例：「单人使用撞不到假 409。**触发重新评估的条件**：开始多人协作，或习惯开多个标签」

「不用跟」底下有好几种形态——已判断不做、已决定的设计边界、条件触发的操作备忘、
待观察项——**不必套用固定标签**，写清楚就行。要紧的是别让读的人无法判断。

不要写「未在本卡范围内处理」这类既不给判断、也不给归宿的话。

**这两类的正确处置是相反的**：「不用跟」应该沉在卡里备查，**不该**进任何待办视图；
「要有人跟」必须有归宿。写法上分不清，两类就都变成噪音。

判断为「不做」**不需要建卡**。往 backlog 里堆永远不会做的卡，会毁掉
「积压本身是信号」这件事（见 `ai/process/kanban.md` 的 WIP 上限）——
以后看到「backlog: 8」将无法判断哪几张是真该做的。

## 不算完成

以下情况不得标记为完成：

- 测试被跳过却没有说明原因。
- 验证只是「看起来没问题」。
- UI 变更了却没有做截图审查。
- UI 用了硬写的一次性色彩／间距，而非 `design-system.md` 的 token；
  或新做的组件没有登记回组件库 inventory。
- 验收标准没有被逐条检查过。
- 实作变更了不相关的文件。
- 发现的风险没有负责人或后续处理。
- 卡片上还有人写的、未回应的决策或提问。

# 审查关卡（Review Gates）

用关卡让人工决策权在流程早期就介入。

## 产品关卡

检查项目：

- 这个问题值得解决吗？
- 非目标是否清楚？
- 用户流程与验收标准是否完整？
- 边界案例是否涵盖？

批准者：

- 人工产品负责人。

## UI Mockup 关卡

检查项目：

- 是否有多个变体？
- 是否涵盖默认、空状态、载入中、错误与行动装置版状态？
- 变体是否以 `ai/context/design-system.md` 既有的 design token 与组件组成（Epic 0 的风格方向阶段除外）？
- 新做的组件是否依既有风格制作、并已登记回组件库 inventory？
- 选定的变体是否符合产品意图？
- 视觉验收标准是否清楚？

批准者：

- 人工产品负责人或设计师。

## 架构关卡

检查项目：

- 计画是否遵循既有模式？
- 是否避免不必要的抽象？
- 数据契约是否清楚？
- 迁移与回滚风险是否已被理解？

批准者：

- 架构 agent，高风险任务再加上人工审查。

## 安全性关卡

检查项目：

- 输入验证。
- 身分验证与授权。
- 密钥处理。
- 注入风险。
- 文件与网络边界。
- 敏感数据的记录行为。
- 依赖包与供应链风险。

批准者：

- 安全性审查 agent，高风险任务需人工批准。

## 验证关卡

检查项目：

- 是否有针对预期行为的测试。
- 回归风险是否已涵盖。
- CI 相关指令是否通过。
- UI 屏幕截图是否已审查（如适用）。

批准者：

- 测试工程 agent 或人工审查者。

## 合并关卡

检查项目：

- Diff 够小。
- 摘要清楚。
- 已附上证据。
- 审查发现已解决或已记录。
- 已记录人工验收。
